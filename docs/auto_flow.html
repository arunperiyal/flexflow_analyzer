1 · One run of auto apply

Checks that cover the whole folder come first. If the queue can't be read, nothing happens to any case, because a case that looks idle might be running.

flowchart TD
  A(["auto show / auto apply"]) --> B{"Remote chosen, and its folder in .cases.yml?"}
  B -->|no| X1["Stop: --remote NAME or use remote:NAME;<br/>auto init --remote NAME --path DIR adds its folder"]
  B -->|yes| C{"squeue and sacct answer cleanly?"}
  C -->|"no: error, or anything on stderr"| X2["Stop: no action on any case"]
  C -->|yes| D{"cloud login: key through the alias, else password from remotes.json"}
  D -->|fails| OFF["Offline: history archive, clean, compile only<br/>no post decisions, uploads or deletions"]
  D -->|ok| E["Read each case: config, files, jobs by WorkDir,<br/>cloud listing and the md5 ledger"]
  OFF --> E
  E --> F["Show the plan: actions, deletions and the check each waits for,<br/>upload size and time at login-node speed"]
  F --> G{"Ask once: delete when checks pass?"}
  G -->|yes| H["For each case, in order:<br/>2 history, 4 finished post, 3 new post, input and program files"]
  G -->|no| H2["Same, with every deletion skipped"]
  H --> I(["Summary, journal, exit code 0 or 1"])
  H2 --> I

2 · History (your steps 1–5, 15)

The run-directory history is only moved when no main job of the case is running, pending or completing. A running solver keeps writing into the moved file, and a queued job's mainFlex.sh archives the same file when it starts. The queue is read again just before the move, so a job submitted in between is caught.

flowchart TD
  A(["Case"]) --> B{"Main job of this case running, pending or completing?<br/>matched by WorkDir, not job name"}
  B -->|yes| S["Leave the run-dir history where it is"]
  S --> U0["Upload a snapshot of the live .othd and .oisd"]
  B -->|no| C{".othd or .oisd in the run directory?"}
  C -->|no| D
  C -->|yes| H1["Read the queue again, then<br/>organise history --update: run dir to archive/"]
  H1 --> D{"An archive/ part not yet in cleaned/?"}
  D -->|yes| H2["organise history --clean --compile"]
  D -->|no| H3
  H2 --> H3["Upload archive/, cleaned/, compiled file<br/>only what the md5 ledger lacks"]
  classDef ok fill:#ddf1e3,stroke:#1d6b3a,color:#0f3a1f
  class U0,H1,H2,H3 ok

3 · Deciding a new post job (steps 6, 16)

The unit is a run. The cloud decides whether it needs converting; the inputs (.out or ASCII PLT) decide whether it can be. A running or queued case can get a post job too.

flowchart TD
  A(["Case"]) --> P0{"Post job of this case pending, running or completing?"}
  P0 -->|yes| W["Wait for it"]
  P0 -->|no| R["Look for the run: .othd in the run dir,<br/>else the newest archive/ part<br/>never cleaned/: --clean rewrites it"]
  R --> RF{"Found?"}
  RF -->|no| NY0["Needs you: archive/ missing or empty<br/>every case keeps archive/ and cleaned/"]
  RF -->|yes| T["t1..t2 = its first and last tsId on the outFreq grid"]
  T --> T2["Cut t2 to the last settled step<br/>and to a queued restart's restartTsId"]
  T2 --> Q{"Binary PLTs of t1..t2 on cloud?"}
  Q -->|all| DONE["Nothing to post"]
  Q -->|none| S1["Post from t1"]
  Q -->|"unbroken t1..k"| S2["Post from k + outFreq"]
  Q -->|"some, with holes"| NY1["Needs you: the missing steps"]
  S1 --> I{"Every step to post has all nsg .out parts,<br/>or its ASCII .plt?"}
  S2 --> I
  I -->|no| NY2["Needs you: no PLT on cloud and no .out here"]
  I -->|yes| QU{"Room in the 2 TB quota for the ASCII PLTs?"}
  QU -->|no| NY3["Needs you: disk quota"]
  QU -->|yes| SUB["run post full, or convert when every step has its ASCII .plt<br/>record the job id and range"]
  classDef stop fill:#f8e1de,stroke:#a3271f,color:#5c1510
  classDef wait fill:#fbefd2,stroke:#8a5a00,color:#4a3000
  classDef ok fill:#ddf1e3,stroke:#1d6b3a,color:#0f3a1f
  class NY0,NY1,NY2,NY3 stop
  class W,DONE wait
  class S1,S2,SUB ok

"Settled": all nsg parts of a step are there and non-empty, the solver has started a later step, and nothing has touched them for 10 minutes. The last tsId in a live .othd is the step being computed, so it never counts.

4 · After a post job (steps 7–11, 17)

Nothing local is deleted until its copy on cloud has the same md5. ASCII PLTs go last of the PLTs, so a binary file that fails to upload can still be made again.

flowchart TD
  A(["Case with a recorded post job"]) --> B{"Its state in sacct"}
  B -->|"pending, running or completing"| W["Wait"]
  B -->|"failed, timeout, cancelled"| NY1["Needs you: post job ended badly"]
  B -->|completed| C{"Every step has a valid binary PLT?<br/>header size, same size as the rest, newer than its .out"}
  C -->|no| NY2["Needs you: the bad steps"]
  C -->|yes| U1["Upload binary PLTs: write .part, then rename"]
  U1 --> V{"md5 on cloud = md5 here?"}
  V -->|no| RE["Send again once; still wrong: needs you"]
  V -->|yes| DEL{"Deleting agreed at the start?"}
  DEL -->|no| RST
  DEL -->|yes| C1["Delete ASCII PLTs of verified steps"]
  C1 --> C2["Delete binary PLTs verified on cloud"]
  C2 --> C3["Delete .out of verified steps<br/>never the step being written, never past a queued restart"]
  C3 --> C4["Thin .rst to the auto.keep_rst grid in .cases.yml<br/>keep the queued restart's set and the newest complete set"]
  C4 --> RST{"Newest complete .rst set on cloud?"}
  RST -->|yes| E(["Done"])
  RST -->|no| U2["Upload it, md5 check"] --> E

6 · What to check

  • Would you have made the same post range for each case above, especially the ones cut at a queued restart (U1P0, U4P0)?
  • Is 10 minutes without change long enough before a step's .out counts as settled on a running case?
  • Should a case with holes on cloud (some PLTs present, some missing) really stop at needs you, or should auto post the missing blocks?
  • Are the .rst sets kept by thinning the right ones: your keep_rst grid, the queued restart's set, and the newest complete set?
  • Is there any step of your manual routine missing from the charts?

The commands the charts belong to:

auto init --remote NAME # that remote's folder and keep_rst, disk_alert in .cases.yml     (built)
auto show [case]        # labelled sections for a case; the table for case:* (--detail)  (built)
auto commands [case]    # just the commands to run, numbered, as plain text              (built)
auto status [case]      # one line per case: state, steps, jobs, what is next           (built)
auto apply [case]       # history, checked uploads, post jobs; deletes nothing yet       (built)
auto log [case]         # what earlier runs did                                          (planned)
